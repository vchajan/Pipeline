# Big Data Pipeline Monitor — Project Blueprint

## 1. Project goal

Build a full-stack application for evidence, execution simulation and monitoring of data pipelines over datasets.

The system simulates tools such as Apache Airflow, Databricks Jobs and AWS Glue, but it is not a real Spark, Airflow or distributed big data platform.

The project must demonstrate architectural design, domain modelling, REST API design, business rules, input validation, error handling, separated business logic, frontend monitoring, authentication/authorization, asynchronous execution, testing and documentation.

## 3. Main architecture

```text
Browser
  |
  v
Nginx
  |
  +------------------------------+
  |                              |
  v                              v
React frontend              FastAPI backend
                                  |
                                  +--> PostgreSQL
                                  |
                                  +--> Redis queue
                                           |
                                           v
                                      RQ Worker

Additional services:
- backend-migrate
- scheduler
- keycloak
- keycloak-db
```

Nginx is the single entry point. FastAPI exposes REST API. PostgreSQL stores persistent state. Redis/RQ decouples API request handling from pipeline execution. Worker processes runs asynchronously. Scheduler creates scheduled runs.

## 4. Course connections

Integration levels:
- Presentation layer: React frontend
- Application/business layer: FastAPI routes and services
- Data/persistence layer: PostgreSQL
- Service/API layer: REST API
- Asynchronous integration: Redis/RQ queue

Integration styles:
- REST API is synchronous request/response.
- Redis/RQ is asynchronous messaging/queueing.
- Nginx acts as a single entry point/reverse proxy.

BPM:
- Pipeline = process definition
- PipelineVersion = versioned process definition
- JobRun = process instance
- JobRunStep = process activity
- AlertRule = decision/business rule
- AlertEvent = incident generated by a rule

DWH and ETL/ELT:
- Dataset = source metadata
- Pipeline = data pump / ETL or ELT process
- JobRunStep = extract / transform / load
- Dashboard = monitoring/analytical view

Big Data concepts:
- engine: python, sql, spark, databricks, aws_glue
- processing_mode: batch, streaming, lambda, kappa
- load_type: full, incremental
- target_layer: staging, l0_raw, l1_clean, l2_mart

Security:
- Authentication through Keycloak
- Authorization through RBAC
- AuditLog for important user/system actions
- Production deployment would require HTTPS/TLS

- id, pipeline_id, version_number, config_json, active, created_at, created_by
- rule: each pipeline can have only one active version

JobRun:
- id, pipeline_id, pipeline_version_id, trigger_type, status, started_at, finished_at, runtime_seconds, records_processed, error_message, created_by, created_at

JobRunStep:
- id, run_id, name, status, started_at, finished_at, records_processed, error_message, order_index
- names: extract, transform, load

AlertRule:
- id, pipeline_id, name, condition_type, threshold_seconds, threshold_records, enabled, created_at, updated_at
- condition_type: run_failed, runtime_exceeded, records_below_threshold, pipeline_not_run_on_schedule, step_failed

AlertEvent:
- id, rule_id, run_id, pipeline_id, message, severity, status, created_at, acknowledged_at, resolved_at, acknowledged_by, resolved_by
- severity: low, medium, high, critical
- status: open, acknowledged, resolved

AuditLog:
- id, actor_user_id, actor_email, action, entity_type, entity_id, metadata_json, created_at

OutboxEvent:
- id, event_type, aggregate_type, aggregate_id, payload_json, processed, created_at, processed_at

WorkerHeartbeat:
- id, worker_id, status, last_seen_at, processed_jobs, current_run_id

SchedulerHeartbeat:
- id, scheduler_id, last_tick_at, status, created_runs_count

## 7. Business rules

Pipeline:
- Pipeline can be created only for an existing Dataset.
- Pipeline must have a name.
- Pipeline can be active or inactive.
- Inactive pipeline cannot be started.
- Pipeline can have only one active PipelineVersion.

Run:
- pending -> queued
- queued -> running
- queued -> cancelled
- running -> success
- running -> failed
- running -> cancelled
- success/failed/cancelled are terminal states.

Alert:
- alert is created when run fails,
- runtime exceeds threshold,
- records are below threshold,
- pipeline did not run on schedule,
- step failed.

Roles:
- viewer: read-only access
- operator: start pipelines, cancel/update runs, acknowledge/resolve alerts
- admin: full access

## 10. Auth blueprint

Primary mode: Keycloak.

Flow:
1. User opens frontend.
2. Frontend redirects to Keycloak login.
3. Keycloak returns JWT token.
4. Frontend sends Authorization: Bearer token.
5. Backend validates token.
6. Backend reads roles from token.
7. Endpoint allows/denies action.

Fallback mode: demo auth.

Header:
- X-Demo-User-Id: 1

Demo users:
- admin / admin123
- operator / operator123
- viewer / viewer123

## 11. Worker blueprint

Queue:
- Redis + RQ
- queue name: pipeline-runs

Worker flow:
1. load JobRun
2. set status to running
3. process extract
4. process transform
5. process load
6. decide success/failed based on config
7. set finished_at/runtime/records_processed
8. evaluate alert rules
9. create alert events
10. write audit logs and outbox events
11. update WorkerHeartbeat

PipelineVersion config example:
```json
{
  "failure_probability": 0.2,
  "min_runtime_seconds": 3,
  "max_runtime_seconds": 10,
  "records_min": 500,
  "records_max": 5000
}
```

## 12. Scheduler blueprint

Scheduler runs as a separate singleton container.

It uses croniter.

Flow:
1. tick every 30 seconds
2. load active pipelines with schedules
3. compute due schedules
4. prevent duplicate scheduled runs
5. create JobRun with trigger_type=scheduled
6. enqueue to Redis/RQ
7. update SchedulerHeartbeat
